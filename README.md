# 🩸 BloodNet
### سامانه هوشمند هماهنگی و مدیریت تأمین فرآورده‌های خونی

BloodNet یک سامانه محلی برای ثبت، مدیریت و پیگیری درخواست فرآورده‌های خونی در محیط شبیه‌سازی است. این سیستم با بررسی سازگاری گروه خونی، موجودی، شرایط اهداکنندگان و وضعیت ارسال، به هماهنگی بهتر میان بیمارستان‌ها، مراکز انتقال خون و اهداکنندگان کمک می‌کند.

> **توجه:** تمام داده‌های بسته تمرین ساختگی هستند. BloodNet یک پروژه آموزشی و شبیه‌سازی است و برای تصمیم‌گیری درمانی یا استفاده با اطلاعات واقعی بیماران طراحی نشده است.

## 🚀 قابلیت‌ها

- ثبت، مشاهده، اصلاح فوریت، تأیید و لغو درخواست‌های خون
- مدیریت درخواست‌ها و رویدادها با استفاده از SQLite
- احراز هویت نمایشی و پشتیبانی از کلید Idempotency
- بررسی سازگاری گروه خونی و نوع فرآورده
- بررسی واجد شرایط بودن اهداکنندگان بر اساس قواعد تعریف‌شده
- انتخاب موجودی سازگار بر اساس نزدیک‌ترین تاریخ انقضا (FEFO)
- پیگیری زمان تخمینی رسیدن محموله (ETA)
- ارتباط با سرویس‌های محلی Gateway، Travel و Inventory
- مدیریت رویدادهای تکراری یا نامرتب
- تفکیک وضعیت اهدای انجام‌شده، تأمین در مسیر و تحویل نهایی
- داشبورد فارسی با پشتیبانی از راست‌چین (RTL)

## 🛠 فناوری‌ها و معماری

| بخش | فناوری | کاربرد |
|---|---|---|
| Backend | Python | زبان اصلی توسعه |
| API | FastAPI | پیاده‌سازی API و منطق سمت سرور |
| Database | SQLite | ذخیره‌سازی پایدار اطلاعات |
| Frontend | HTML5 | ساختار صفحات |
| Styling | CSS3 | طراحی رابط کاربری |
| JavaScript | Vanilla JavaScript | تعاملات و ارتباط با Backend |
| Communication | HTTP / JSON | تبادل اطلاعات میان سرویس‌ها |
| Server | Uvicorn | اجرای برنامه FastAPI |

Backend مسئول مدیریت منطق اصلی سیستم، اعتبارسنجی درخواست‌ها، ذخیره‌سازی اطلاعات و ارتباط با سرویس‌های مختلف است.

Frontend نیز رابط کاربری را فراهم می‌کند و از طریق درخواست‌های HTTP با Backend در ارتباط است.

رابط کاربری با HTML، CSS و JavaScript ساده توسعه داده شده و برای اجرای آن نیازی به مرحله جداگانه Build وجود ندارد.

برای آشنایی بیشتر با اجزای سیستم و جریان اطلاعات، به [مستند معماری](docs/ARCHITECTURE.md) مراجعه کنید.

### بسته محلی مسابقه

اجرای کامل پروژه و تست‌های یکپارچه به پوشه‌های `participant_kit/` و `harness/` نیاز دارد.

این پوشه‌ها در محیط توسعه باید کنار README قرار داشته باشند. به دلیل در دسترس نبودن مجوز بازتوزیع عمومی فایل‌های ارائه‌شده توسط برگزارکننده، این پوشه‌ها و همچنین `starter/` عمداً در Git نادیده گرفته شده‌اند.

برای اجرای کامل پروژه، بسته مجاز را جداگانه از برگزارکننده دریافت کنید.

## 💻 پیش‌نیازها

- Windows 10 یا 11
- Python 3.12
- Node.js فقط برای بررسی نحوی JavaScript
- بسته محلی `participant_kit/` و `harness/` برای اجرای کامل و تست‌ها

## ⚙️ نصب و راه‌اندازی

ابتدا ترمینال PowerShell را در مسیر اصلی پروژه باز کنید.

**۱. ایجاد محیط مجازی**

```powershell
py -3.12 -m venv .venv312
```

**۲. نصب وابستگی‌ها**

```powershell
.\.venv312\Scripts\python.exe -m pip install -r requirements.txt
```

**۳. ایجاد فایل تنظیمات محلی**

```powershell
Copy-Item .env.example .env
```

ساخت فایل `.env` اختیاری است؛ زیرا برنامه دارای مقادیر پیش‌فرض محلی است.

مقادیر موجود در `.env.example` نمایشی هستند و نباید برای سرویس واقعی استفاده شوند.

## ▶️ اجرای برنامه

برای دریافت موجودی زنده از سرویس‌های شبیه‌سازی، ابتدا سه سرویس زیر را در سه پنجره جداگانه PowerShell اجرا کنید.

**۱. Gateway**

```powershell
.\.venv312\Scripts\python.exe -m harness.mock_gateway --port 9100 --speed 240
```

**۲. Travel**

```powershell
.\.venv312\Scripts\python.exe -m harness.travel_service --port 9200 --speed 240
```

**۳. Inventory**

```powershell
.\.venv312\Scripts\python.exe -m harness.inventory_service --port 9300 --speed 240 --kit participant_kit
```

**۴. اجرای Backend**

در پنجره چهارم PowerShell:

```powershell
$env:DB_PATH = 'run_out\local-demo.db'
$env:SELF_URL = 'http://127.0.0.1:8000'

.\.venv312\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

### آدرس‌های دسترسی

| بخش | آدرس |
|---|---|
| داشبورد | http://127.0.0.1:8000/ |
| مستندات تعاملی API | http://127.0.0.1:8000/docs |
| بررسی سلامت سرویس | http://127.0.0.1:8000/health |

> سرویس‌های محلی صرفاً برای توسعه و شبیه‌سازی هستند. اگر سرویس Inventory در دسترس نباشد، سیستم خطای سرویس را گزارش می‌کند و موجودی ساختگی نمایش نمی‌دهد.

## 🔌 مسیرهای API

| متد | مسیر | کاربرد |
|---|---|---|
| `GET` | `/health` | بررسی سلامت سرویس |
| `GET` | `/hospitals` | دریافت فهرست بیمارستان‌ها |
| `POST` | `/requests` | ثبت درخواست |
| `GET` | `/requests` | مشاهده درخواست‌ها |
| `GET` | `/requests/{request_id}` | مشاهده جزئیات درخواست |
| `POST` | `/requests/{request_id}/approve` | تأیید درخواست |
| `POST` | `/requests/{request_id}/amend` | اصلاح درخواست |
| `POST` | `/requests/{request_id}/cancel` | لغو درخواست |
| `POST` | `/callbacks/donor-response` | دریافت پاسخ اهداکننده |
| `POST` | `/callbacks/donor-progress` | پیگیری وضعیت اهدا |
| `POST` | `/callbacks/gateway-status` | دریافت وضعیت Gateway |
| `GET` | `/operations/snapshot` | دریافت وضعیت عملیاتی |

برای مشاهده قرارداد کامل درخواست‌ها، Callbackها و پاسخ‌ها، به [مستند API](docs/API_CONTRACT.md) مراجعه کنید.

## 🧪 اجرای تست‌ها

برای اجرای تست‌ها، محیط Python و بسته محلی مسابقه باید آماده باشند.

**۱. اجرای تست‌های واحد و یکپارچه**

```powershell
.\.venv312\Scripts\python.exe -m unittest discover -s tests -v
```

**۲. بررسی کامپایل فایل‌های Python**

```powershell
.\.venv312\Scripts\python.exe -m compileall -q app tests
```

**۳. بررسی نحوی JavaScript**

```powershell
node --check frontend\static\app.js
```

**۴. اعتبارسنجی بسته محلی**

```powershell
.\.venv312\Scripts\python.exe tests\validate_public_kit.py
```

### تست قرارداد API

برای اجرای این تست، Backend باید در حال اجرا باشد:

```powershell
.\.venv312\Scripts\python.exe -m harness.contract_tests --team http://127.0.0.1:8000
```

راهنمای اجرای سناریوها در [مستند Demo](docs/DEMO.md) قرار دارد.

> هر سناریو را با دیتابیس جدا اجرا کنید؛ زیرا ساعت شبیه‌سازی در هر اجرا از صفر آغاز می‌شود. Runner سرویس‌های محلی را خودش اجرا می‌کند؛ بنابراین Mockهای دستی را هم‌زمان روی همان پورت‌ها اجرا نکنید.

## 🔧 پیکربندی

متغیرهای محیطی قابل تنظیم:

| متغیر | مقدار پیش‌فرض | توضیحات |
|---|---|---|
| `PORT` | `8000` | پورت API |
| `SELF_URL` | `http://127.0.0.1:8000` | نشانی Callback سرویس |
| `GATEWAY_URL` | `http://localhost:9100` | ساعت شبیه‌سازی و پیام‌ها |
| `TRAVEL_URL` | `http://localhost:9200` | سرویس محاسبه زمان مسیر |
| `INVENTORY_URL` | `http://localhost:9300` | سرویس موجودی و ارسال |
| `HOSPITAL_TOKEN` | `hospital-token` | توکن نمایشی بیمارستان |
| `COORDINATOR_TOKEN` | `coordinator-token` | توکن نمایشی هماهنگ‌کننده |
| `ABUSE_RARE_DEMAND_TAIL` | `0.02` | سهم انتهایی تقاضای تاریخی برای بازبینی |
| `ABUSE_BURST_WINDOW_MINUTES` | `5` | پنجره بررسی درخواست‌های متوالی |
| `ABUSE_BURST_REQUESTS` | `5` | تعداد درخواست در پنجره برای بازبینی |
| `KIT_PATH` | `participant_kit` | مسیر بسته داده محلی |
| `DB_PATH` | `bloodnet.db` | مسیر دیتابیس محلی |

## ⚠️ محدودیت‌ها

- سیاست بازبینی تقاضای غیرمعمول، یک قاعده قابل تنظیم و مبتنی بر داده تاریخی است؛ نه یک تشخیص‌گر آموزش‌دیده.
- برنامه به‌صورت محلی و تک‌فرآیندی اجرا می‌شود.
- دسترس‌پذیری بالا (High Availability) پیاده‌سازی نشده است.
- احراز هویت تولیدی پیاده‌سازی نشده است.
- سیستم برای استفاده بالینی طراحی یا اعتبارسنجی نشده است.

برای مشاهده فهرست کامل قابلیت‌های آزمایشی و پیاده‌سازی‌نشده، فایل [DECLARED.md](DECLARED.md) را مطالعه کنید.
