# معماری BloodNet

BloodNet یک Backend مبتنی بر FastAPI است. SQLite وضعیت پایدار را نگه می‌دارد، قواعد دامنه از بستهٔ دادهٔ محلی خوانده می‌شوند و ارتباط با Gateway، Travel و Inventory از طریق HTTP انجام می‌شود. رابط وب در همان فرایند Backend ارائه می‌شود.

## اجزای سامانه

| مسیر | مسئولیت |
|---|---|
| `app/api.py` | مسیرهای HTTP، احراز هویت، اعتبارسنجی ورودی و هماهنگی گردش درخواست |
| `app/domain.py` | سازگاری خون، صلاحیت اهداکننده، تعویق، مسیر، رتبه‌بندی و قاعدهٔ بازبینی تقاضا |
| `app/database.py` | طرح SQLite، مهاجرت افزایشی و ذخیرهٔ درخواست، callback، دعوت، ارسال، تعهد و گزارش رخداد |
| `app/integrations.py` | ارتباط غیرهم‌زمان با Gateway، Travel و Inventory، تلاش مجدد محدود و cache زمان مسیر |
| `app/config.py` | خواندن تنظیمات محیط و تعیین مسیر داده و دیتابیس |
| `app/main.py` | نقطهٔ ورود ASGI برای اجرای Uvicorn |
| `frontend/` | رابط HTML/CSS/JavaScript فارسی که توسط FastAPI ارائه می‌شود |
| `participant_kit/` | داده‌ها، قواعد و قرارداد موردنیاز اجرای محلی |
| `harness/` | سرویس‌های محلی و ابزار اجرای سناریو برای توسعه |

`participant_kit/` و `harness/` در Git عمومی این مخزن قرار نمی‌گیرند تا وضعیت مجوز بازتوزیع آن‌ها روشن شود. اجرای کامل محلی به نسخهٔ مجاز این بسته‌ها نیاز دارد.

## جریان درخواست تا تأمین

1. بیمارستان درخواست را همراه token و `Idempotency-Key` می‌فرستد. ثبت کلید و درخواست در SQLite تراکنشی است تا تکرار همان درخواست، رکورد تازه نسازد.
2. درخواست طبق قاعدهٔ پیکربندی‌شده باز می‌شود یا به `pending_review` می‌رود. درخواست در این وضعیت تا تصمیم هماهنگ‌کننده وارد گردش تأمین نمی‌شود.
3. موجودی منقضی یا ناسازگار کنار گذاشته می‌شود. واحدهای انتخاب‌شده بر مبنای نزدیک‌ترین تاریخ انقضا گزینش و با کلید پایدار ارسال می‌شوند.
4. اگر هنوز نیاز باقی باشد، اهداکننده‌ها بر اساس گروه خونی، فرآورده، سن، وزن، سابقهٔ اهدا، تعویق، ساعت سکوت، مسیر و پیام‌های قبلی پالایش و مرتب می‌شوند.
5. پذیرش و پیشرفت اهداکننده از Gateway به شکل callback می‌رسد. شناسهٔ هر رویداد ثبت می‌شود و رویداد تکراری دوباره اعمال نمی‌شود؛ ترتیب زمانی برای callbackهای نامرتب بازسازی می‌شود.
6. پذیرش دعوت به‌تنهایی تأمین محسوب نمی‌شود. پس از callback اهدای کامل، واحد تا پایان پردازش و زمان حمل در وضعیت در مسیر می‌ماند و در ETA تحویل به بیمارستان به مقدار تأمین‌شده افزوده می‌شود.
7. وضعیت ارسال موجودی نیز تا ETA اعلام‌شده در حالت در مسیر می‌ماند. مقدار در مسیر از تقاضای آزاد کسر می‌شود تا همان واحد دوباره تخصیص پیدا نکند.
8. لغو، انقضا یا تکمیل درخواست، پیام‌های ادامهٔ دعوت را متوقف می‌کند. تصمیم‌ها در گزارش رخدادهای SQLite ثبت می‌شوند.

زمان تصمیم‌های شبیه‌سازی از ساعت Gateway گرفته می‌شود، نه ساعت دیواری سیستم.

## پایگاه‌داده و هم‌زمانی

SQLite مرجع پایدار محلی است. ایجاد درخواست، ثبت callback و رزرو اهداکننده از تراکنش استفاده می‌کنند. تغییر طرح فقط با مهاجرت افزایشی انجام می‌شود. رکورد اهدای قدیمی هنگام مهاجرت به‌عنوان تحویل‌شده حفظ می‌شود تا مقدار تأمین‌شدهٔ قبلی کاهش پیدا نکند.

فایل پیش‌فرض `bloodnet.db` دادهٔ محلی است و از Git مستثنا شده. برای هر اجرای آزمایشی ساعت‌دار، مقدار تازه‌ای برای `DB_PATH` انتخاب کنید؛ دیتابیس قبلی را بازنشانی نکنید.

## مسیرهای ارتباطی

- API برنامه: سلامت، بیمارستان‌ها، درخواست‌ها، تأیید، اصلاح، لغو و callbackها.
- snapshot داشبورد: `GET /operations/snapshot?hospital_id=...` با token بیمارستان. در صورت از دسترس خارج‌شدن Inventory پاسخ خطا داده می‌شود.
- Gateway محلی: به‌طور پیش‌فرض درگاه `9100`.
- Travel محلی: به‌طور پیش‌فرض درگاه `9200`.
- Inventory محلی: به‌طور پیش‌فرض درگاه `9300`.
- مستندات تعاملی API: `/docs` در همان نشانی Backend.

## محدودهٔ اجرا و امنیت

برنامه برای اجرای محلی و تک‌فرآیندی ساخته شده است. tokenهای ثابت بسته فقط برای تمرین‌اند. این معماری، دسترس‌پذیری بالا، مدیریت هویت تولیدی یا نگه‌داری دادهٔ پزشکی را فراهم نمی‌کند و برای استفادهٔ بالینی ارزیابی نشده است.
